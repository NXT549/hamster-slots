## The platform layer

*Built for the web (step 3.6, D114); the other columns are the plan.* The game logic never knows which platform it's on (rule 1). Everything platform-specific goes through one small interface, and each platform brings its own implementation:
- `src/platform/platform.ts`: the `Platform` interface: **storage**, **lifecycle**, **`now()`** (the clock) and **achievements**.
- `src/platform/web.ts`: the web version (localStorage, `visibilitychange` + `pagehide`, `Date.now()`, no achievements). `main.ts` calls `boot(createWebPlatform())`: a Steam or mobile build would pass its own platform there instead.
- `src/platform/save.ts` (the save and the settings) and `autosave.ts` (the timer, save on hide/close, pay for a hidden tab's time) only use the interface, so every platform shares them.
- `src/platform/memory.ts`: a pretend platform for the tests.

The save backup (`src/platform/savecode.ts`, 3.8) needed no new service: it only uses storage and `now()`, so every platform gets it. App actions (Quit, open a link) come when a platform needs them.

| Service | What the game needs | Web / itch.io | Steam (Electron or Tauri) | Mobile (Capacitor) |
|---|---|---|---|---|
| **Storage** | Read/write the save and the settings as text, under two keys (settings survive Reset) | `localStorage` (one per site) | A file in the app's user-data folder; Steam Cloud can sync that folder | Native key-value storage (e.g. Capacitor Preferences) rather than the webview's `localStorage` (iOS may clear that when storage runs low) |
| **Save backup** | Export the save as a text string; import one | Copy and paste the text: built (Menu → Save backup, D116). A file download/upload is optional | Same | Same (the share sheet helps) |
| **Lifecycle** | "Going away" → save now and remember when; "back" → pay offline earnings (DESIGN §15) | `visibilitychange` + `pagehide` | Window hidden/minimised, and quitting | App pause/resume events |
| **Clock** | Real-world time, only for offline earnings | `Date.now()` | Same | Same |
| **Achievements** | Unlock one by id | Nothing: the in-game Hamster Diary is the achievement list | Steam achievements through a Steamworks library for the chosen wrapper | Maybe Game Center / Google Play Games |
| **App actions** | Quit, open a link | Not needed (no Quit button on the web) | A Quit button | The Android back button |

- Whether Steam achievements mirror the Diary stickers (ids from data.json) is a **design question for the user**, answered when Steam is planned.
- Keep the interface small. Add a service only when a platform really needs it.

## Platform notes

**Every platform**
- **Fonts:** bundled with the build since 0.2.0 (Fontsource packages; both fonts are OFL-licensed, so that's allowed, D22, D117). Nothing loads from the internet, so offline, desktop and mobile look the same.
- **A save belongs to one site or app.** Saves on `localhost`, on GitHub Pages and on itch.io are three separate saves. Export/import is how a player moves one, and it's the backup when a browser clears a site's data.
- **Big numbers:** break_eternity.js lets currency grow far past 1e308, where plain JS numbers turn into `Infinity`. The save stores them as text so they survive JSON (save v8, step 3.7, D115).
- **The debug panel:** always there in `npm run dev`; in a built game only with `?debug` in the address (D110 default, built in 3.9, D117). A desktop or mobile build will need its own way in (a launch flag, say) if it's wanted there.
- **Store rules:** slot machines, bets, the card gamble and the capsule gacha can trigger "simulated gambling" and loot-box ratings, even with no real money. Check each store's current rules before a release (DESIGN §11, "Things to keep in mind for release").

**Web: GitHub Pages**
- A project site lives at `https://<user>.github.io/<repo>/`, so the build must work from a sub-path (Vite's `base`: `'./'` or `'/<repo>/'`).
- Vite gives built files hashed names, so a browser never mixes old and new files. The dev server always serves fresh files too, so the no-cache Python server (D48) was removed in 3.1.
- `main` deploys itself, so `main` must always be playable (AGENTS → Git and releases).
- The workflow (`.github/workflows/deploy.yml`, D118): on a push to `main` (or by hand: Actions → Run workflow), job 1 runs `npm ci`, `npm test` and `npm run build` on Linux with Node 24, and uploads `dist/`; job 2 deploys it, only if job 1 passed. One deploy at a time.
- The repo is https://github.com/NXT549/hamster-slots; the site is https://nxt549.github.io/hamster-slots/: its own address, so its save is separate from play.bat's (`localhost:8765`). Moving a save there = Menu → Save backup.

**itch.io**
- An HTML5 game is a zip with `index.html` at its root. itch plays it inside an iframe on its own domain, so the build must use relative paths (Vite `base: './'`).
- Set the embed size (or allow fullscreen). The game already fits phone widths.
- Upload by hand at first; itch's `butler` command-line tool can automate it later.

**Steam (Electron or Tauri: to be decided)**
- **Electron** bundles its own Chromium: the same browser engine on every OS and mature Steamworks libraries, but a big download (roughly 100 MB or more).
- **Tauri** uses the system's webview (WebView2 on Windows, WebKit on macOS and Linux): a small download, but each OS draws a little differently (test with WebKit, i.e. Safari), and its native side is written in Rust.
- Either way: saves become files through the platform layer (with Steam Cloud), a Quit button appears, and the game must keep running, or pay offline earnings, while the window is hidden (browsers slow hidden pages down).

**Mobile (Capacitor, maybe)**
- Touch only: no hover and no keyboard. The keyboard shortcuts (bet `-`/`=`, the gamble keys, the backtick debug panel) need on-screen ways in, buttons need finger-sized targets, and the layout must keep clear of notches (safe areas).
- Save when the app pauses; pay offline earnings when it resumes.
- Audio already starts on the first tap (DESIGN §15), which mobile browsers require.
- Apple and Google each have their own rules and age ratings for simulated gambling. Check them before building for mobile.

## Invariants any rewrite must keep

These were the "gotchas for the port". They still hold for the TypeScript migration: the same data and the same seed must give the same game, down to the cent.

- **Payout tables are keyed by strings:** `payouts["seed"]["2"]`, not `[2]` (in TypeScript: `Record<string, number>`).
- **The cost formula is exactly `floor(baseCost × growthRate ^ owned)`** (`costAtLevel()`), so costs never drift (rule 3).
- **Money is rounded to cents after every change** (`roundMoney()`, D12), and money maths goes through money.ts (D115): break_eternity's own `div`, `pow` and `round` differ from plain numbers in the last digit, which would drift by a cent.
- **Seed formula epsilon:** `seedsForCoins()` is `floor(pow(coins / divisor, exponent) + 1e-9)`. Without the tiny `+ 1e-9`, an exact square like 11,700 coins (3 seeds with the square root, `seedExponent` 0.5) can come out as 2.9999999 and floor to 2 seeds. Keep it.
- **Offline earnings are capped, then halved:** `min(seconds, maxSeconds) × perSecond × efficiency`. Compare `seconds >= minSeconds` BEFORE capping.
- **Sprite scale must stay a whole number** (`max(1, floor(size / width))`), or pixel art gets uneven pixels.
- **Tokens and skins survive retiring.** They're outside the list of fields `retire()` resets. Only a full Reset clears them.
- **Retire keeps lifetime stats but resets the rest:** copy the list of reset fields from `retire()` exactly (coins, upgrades, machines, active machine, delivery, auto timer, run totals), then re-apply "start with" traits.
- **mulberry32 must stay bit-exact** (`>>> 0` and `Math.imul` in `src/logic/rng.ts`), so the same seed gives the same spins before and after the migration.
- **Spin results are `result[reel][row]`** (save v5). A v4 save's flat result becomes one-row columns; check the row count against the machine's `rows` when loading.
- **Multi-line payouts round each line to cents, then add them up.** Rounding the total once gives different cents, and then payouts won't match.
- **EV scales with lines, the hit rate doesn't** (D62). Keep the exact reel-1-and-2 count for the hit rate, and cache it; it needs every 2-match to pay (a data test checks this).
- **An upgrade a machine doesn't sell is level 0 on that machine**, even if the save has a number for it. "Start with" traits only raise the level on machines that sell the upgrade (the Heirloom Reel never gives the Stacker a third reel).
- **The free first machine is always owned.** When loading, add it back if it's missing, keep each machine type once, and find the active machine by its type id (indexes can shift during cleanup).
- **The wild "best of" rule compares BASE payouts,** then applies Jackpot Dance only if the chosen reading covers every reel. Comparing after multipliers gives different wins.
- **A scatter never counts on a line and ends a run**, even after wilds: wild, wild, ball pays the 2-wild prize; wild, ball pays nothing.
- **Order of RNG draws in `resolveSpin`** (for seeded parity): evaluate the lines (no draws) → golden-jackpot tokens → start free spins (no draw) → start the jackpot wheel (**one `pickWeighted` draw** for the pot) → offer the gamble (no draw). `gamble()` uses one `rng.next()` per pick. Keep this order.
- **Pots are in base units** (before the bet and payout bonuses). Growth is added on **paid** spins only, and a won pot resets to its seed, not to 0.
- **Gamble coins never go through `earn()`**, and the open gamble is removed in `toSaveData()`.
- **The queued click is not state**: don't save it, and clear it on switch, retire and load.
- **Tick order** (every 1/60 s): delivery → jackpot wheels (all machines) → spin timers (all machines) → gamble offer countdown → the queued click → free spins (active machine) → auto-spin (held while free spins, a wheel or a gamble has the machine) → Self-Starter.
- **The weights the reels use (M7), in this order:** locked symbols → 0 (unless their unlock is open) → family weight shifts (skipped when either symbol has weight 0) → the Hamster Wild's added weight → × (1 + Luck ÷ 100) on every symbol except the blank. A different order gives different odds.
- **An unlock upgrade opens its list in order:** level n = the first n symbols. The v6 → v7 migration sets every unlock a machine sells to its max level (so `migrateSave` needs the data file).
- **A blank ends a run and never pairs,** even with a wild next to it: wild, blank = nothing; wild, wild, blank = the 2-wild prize.
- **The multi-line hit rate** (machine.ts `gridHitRate`): try every way reel 1's rows can land, then multiply, over reel 2's rows, the chance that that cell pairs with none of its lines' reel-1 cells. It's exact and fast (8 symbols on 3 cells = 512 cases), and the answer is cached by weights.
- **The auto-spin interval** is `max(baseInterval × multiplier^(level−1) × Quick Paws, spin time (with Quick Paws) + rest)`, and the spin time depends on the machine, so ask per machine.
- **The card draw** is `SUITS[floor(rng.next() × 4)]` with SUITS in the order hearts, diamonds, clubs, spades: one draw per pick. Keep it for seeded parity.
- **`pickWeighted`'s float-rounding fallback** returns the last item with weight > 0 (a locked symbol must never land).

## Decisions

Newest at the bottom. Format: **decision**, *alternatives rejected*, why.

> **D1–D105 were written while a Godot rebuild was planned.** Their Godot remarks ("Godot: …", "ports to GDScript", "Godot needs") are history: since D106 there is no engine port. The decisions themselves still stand unless a later one says otherwise.

**D1 — A local server (`play.bat`) to run the game.** *Rejected: `data.js` wrapper, drag-in file picker.*
Browsers block a page opened from disk (`file://`) from reading `data.json`. A tiny Python server (`python -m http.server`) avoids that and keeps `data.json` pure JSON that Godot can load as-is. As a bonus it enables the debug panel's "Reload data.json" button and ES modules (`import` / `export`). (Since milestone 3 it's `tools/serve.py`, the same server with no caching; see D48.)

**D2 — Spins cost coins; food deliveries are the safety net.** *Rejected: free spins.* (User's call.)
It gives the real slot-machine feeling of "is this spin worth it?". Soft-locking at 0 coins is solved by deliveries: a timed job that always pays, needs no luck, and can always be started. The balance rules in DESIGN.md §9 keep deliveries weaker than auto-spinning.

**D3 — Count matches from the left.** *Rejected: pay any pair anywhere; 3-in-a-row only.*
This is how real slots read a payline. It works for any reel count (2 → 5+). The payout table is keyed by match count (`"2"`, `"3"`, …), so adding a reel means adding a key, not new code.

**D4 — No power while the hamster is delivering.** *Rejected: deliveries run alongside spinning.*
The hamster runs the wheel that powers the machine, so this is thematically consistent. It also makes deliveries a real choice (safe and slow vs risky and fast) instead of free extra income. A spin already in progress still finishes, since it was paid for.

**D5 — The machine starts at 2 reels and progresses by upgrades.** (User's idea.)
Old Clunky starts with 2 reels, and the Third Reel upgrade adds one. Newer machine types (Retro, Modern) come in milestones 4–5. State stores `machines: [...]` as an **array from day one**, even with a single machine, so going multi-machine later isn't a refactor.

**D6 — Upgrades have a `scope`: `global` or `machine`.**
Chubby Cheeks and Wheel Training belong to the hamster (global). Oiled Lever and Third Reel belong to a machine, so a new machine type starts fresh. Machine levels live in `state.machines[i].upgrades`, global ones in `state.upgrades`.

**D7 — Upgrade effects are data (`effect.type` + params); the logic has one small function per type.**
Types: `payoutMultiplier`, `autoSpin`, `spinCostMultiplier`, `extraReel` (plus the Family Tree types, D30). A new upgrade of an existing type needs only `data.json`. A new *type* needs one small function in `game.js` (it reads its levels via `effectsOfType()`) and an entry in `STAT_FOR_EFFECT` for the shop preview.

**D8 — Expected value comes from a formula, not from sampling.** `expectedValue()` in `machine.js` gives exact EV, hit rate and RTP, used by the debug panel and the tests. The test then *samples* 200k spins to check that the formula and the RNG agree. If machines get too complex for a formula (wilds, many paylines), switch to exact enumeration or simulator estimates.

**D9 — A seedable RNG (mulberry32) passed into the game.** *Rejected: `Math.random()`.*
The same seed gives the same results, so tests and balance simulations can be repeated exactly. The logic files never call `Math.random()`. mulberry32 is about 6 lines and ports to GDScript (mask to 32 bits).

**D10 — A fixed 60 Hz logic tick.** `update(dt)` saves time up in an accumulator and runs `tick(1/60)` as many times as fits. One `update(10)` gives exactly the same result as 600 × `update(1/60)`, so 50× speed, lag spikes and (later) offline progress all stay deterministic. This mirrors Godot's `_physics_process` (60 Hz by default). Side effect: timers resolve to the next 1/60 s.

**D11 — The spin result is decided at spin start and paid at spin end.** The UI needs to know where each reel will stop, and the logic stays in charge of timing (`spinDuration`). The UI only *reads* `getSpinProgress()` to animate, so speed-up and fast auto-spin just work.

**D12 — Money is rounded to cents after every change.** `roundMoney()` in `game.js`. With spin costs like 5 × 0.9ⁿ and payouts × 1.25, raw floating-point sums drift (4.4999999…) and could make "4.5 coins" unable to pay a 4.5 spin. Godot floats are 64-bit doubles too, so use the same rounding there.

**D13 — `save.js` only moves text to and from `localStorage`. The save format (`toSaveData`, `loadSaveData`, migrations, cleanup) lives in `game.js`.**
Keeping the format in the logic means the Node test can check save round-trips and cleanup headless, and the Godot `SaveManager` only has to swap `localStorage` for `FileAccess`.

**D14 — Auto-spin carries leftover time; it doesn't bank spins.** When the timer passes the interval it fires and subtracts the interval, so the average rate is exact even with 60 Hz ticks. If it can't fire (busy, broke, delivering), it waits *at* the interval instead of stacking up extra spins.

**D15 — Wheel Training max level is 8, not 10.** At level 8 the interval (2.5 × 0.85⁷ ≈ 0.80 s) reaches the 0.8 s spin time. Levels 9–10 would cost coins and do nothing.

**D16 — Holding Space does NOT repeat spins.** *Rejected: key auto-repeat spins.* Held keys fire repeated `keydown` events. If those spun, holding Space would be a free max-speed auto-spinner and Wheel Training would be pointless. Each spin needs a tap. (Godot: use `Input.is_action_just_pressed("spin")`, not `is_action_pressed`.)

**D17 — Reels stop left to right at fixed points of the spin progress** (reel 1 at 30%, the last at 90%), so the last reel lands just before the payout. The "flicker" while spinning uses the real clock and never the game RNG, so drawing can't change results.

**D19 — The UI is a "diorama", not a clicker layout.** *Rejected: keep the three-column Cookie Clicker style.* User feedback: it looked too much like Cookie Clicker. Now there's a room stage (wall, floor, the wheel belted to the machine), a HUD pill on top, and a tabbed tray below. This previews the Godot 2.5D scene, where the machine and wheel are physical objects in a room and the UI is an overlay.

**D20 — Sprites are text grids in `js/art.js` with a shared palette.** *Rejected: CSS-shape art, image files.* Anyone can edit them in a text editor, `tools/test_art.mjs` catches typos, and a **skin can be a palette swap** (the Rare and Epic capsules are literally `recolor(capsule)`; fur skins recolour the hamster). For Godot: export each grid to a PNG (a small tool can do this later) and import with the Nearest filter.

**D21 — Reels are scrolling strips with 3 visible rows,** positioned from `game.getSpinProgress()`. That keeps them exact at any game speed. The rows above and below the payline are decoration, picked with `Math.random()` in the view only, never the game RNG.

**D22 — Two fonts: Pixelify Sans (weight 500) for words, Nunito for numbers and body text.** In the pixel font, 5 and 8 read as "S", and in bold its C reads as O. Both fonts are OFL-licensed, so they can be bundled with Godot. The web version loads them from Google Fonts and falls back to system fonts offline.

**D23 — Theme tokens in `style.css :root`** (colours, radii, fonts, cell size). Skins and the final art direction change tokens, not rules. Godot: a `Theme` resource plus a palette resource.

**D24 — Reset is a two-tap button inside the Menu,** not the browser's `confirm()` pop-up. It looks consistent and ports directly to Godot, which has no `confirm()`.

**D25 — Highlights go BEHIND symbols.** A translucent gold overlay on top of the payline made grey Sunflower Seeds look like Golden Seeds, which misleads the player about what they won. The rule: never tint a symbol; glow behind it or outline around it.

**D18 — No catch-up for background time (yet).** The frame loop caps each frame at 0.25 s of real time, and browsers pause `requestAnimationFrame` in hidden tabs, so the game only runs while visible. Offline earnings are planned for the Feel milestone (now milestone 4). It'll be one `update(secondsAway)` call (capped), which the fixed tick already handles exactly.

**D26 — Rebirth = "Retire to the Big Cage"; the currency is "Heirloom Seeds".** (User picked "retire & pass it on" and "a permanent tree bought with rebirth currency".) *Rejected: the old placeholder name "Golden Sunflower Seeds".* It clashes with the **Golden Seed** reel symbol, so players would mix up a jackpot symbol with a currency. "Heirloom" fits the theme: seeds passed down a family.

**D27 — Seeds come from LIFETIME coins earned: `total = floor((lifetime / 5000) ^ 0.5)`, and retiring pays `total − seeds already received`.** *Rejected: a formula on this life's coins only.* With a square root, per-life seeds reward retiring every few minutes (small lives give more seeds per coin). That's an exploit and it's tedious. The lifetime version gives the same seeds for the same coins however often you retire (tested). Cookie Clicker's heavenly chips work this way.

**D28 — Heirloom bonus: every seed EVER earned gives +10% payouts, even after it's planted.** *Rejected: (a) tree-only power; (b) AdVenture-Capitalist style "unspent seeds give the bonus".* (a) A bot showed lives stretching to ~90 min by generation 4: a finite tree can't keep up with a square-root formula. (b) It makes planting feel like losing power. With the bonus counted on seeds *earned*, planting is always a pure gain. 0.05 vs 0.10 was compared in the bot: 0.10 finishes the tree ~30 min sooner and makes lives 3–5 feel quicker.

**D29 — Payout bonuses: add up within a group, multiply between groups: `(1 + coin upgrades) × (1 + family)`.** *Rejected: everything additive.* If Family Pride's +25% were added to Chubby Cheeks' +500%, it would barely matter. Multiplying keeps family traits meaningful all game. Family group = heirloom bonus + Family Pride + Family Fortune.

**D30 — Family Tree nodes use the SAME shape as upgrades** (`baseCost`, `growthRate`, `maxLevel`, `effect`) plus `branch` and `requires`, and the same cost formula. The logic collects effects from both lists in one place (`effectsOfType()` in game.js), so a tree node can reuse an upgrade effect type (Family Pride is a `payoutMultiplier`). New effect types: `shiftWeight`, `fullLineMultiplier`, `startingLevel`, `spinSpeed`, `deliveryTime`, `deliveryPayoutBonus`, `autoDelivery`, one small function each.

**D31 — "Start with" traits write real upgrade levels** (at retire, when planted, and on load), and never lower a level the player bought. *Rejected: computing "effective level = max(bought, free)" on the fly.* A single stored number is simpler to read, save and port. The cost formula counts the free level as owned (the next Wheel Training costs 125), which is fair.

**D32 — Luck = moving weight between symbols (`shiftWeight`), not adding weight.** Weights on Old Clunky still sum to 100, so "weight" reads directly as "% chance per reel". The shift never takes a symbol below weight 1. A machine without those symbols ignores the effect (future machines).

**D33 — The Family tab appears only when the first seed is pending.** *Rejected: showing it from the start.* A new player doesn't need a second currency in minute one. The reveal ("I've earned an Heirloom Seed!…") is a nice mid-game surprise, and the tab gets a dot until opened.

**D34 — The Family Tree is drawn top-down like a genealogy chart** (Roots on top, three branch columns), and buying is **select → Plant** in a detail panel. *Rejected: a buy button on every node* (too cramped at phone width, and too easy to mis-tap). Retire is two-tap, like Reset.

**D74 — Bets: one global unlock (High Roller), a chosen bet per machine, and a "step down" rule.** A spin costs spin cost × bet and every payout is × bet, so the bet never changes the RTP. *Rejected: a per-machine bet unlock* (a newly bought machine would start at ×1 and earn less than the old one at ×10, so buying a machine would feel like a loss). A new machine starts at the bet you were using. **If the chosen bet is unaffordable, the spin uses the biggest unlocked bet you can afford**, and it's refused only below ×1; *rejected: refusing the spin* (a high bet would silently stall auto-spin for idle players). Win tiers keep using the BASE payout ÷ BASE spin cost (D54), so the bet can't turn wins into "big wins". `getSpinCost()` keeps meaning "×1 after upgrades"; `getBetCost()` / `getSpinBet()` are new.

**D75 — The wild uses the real-pokie "best of two readings" rule.** A line is read as j leading wilds (pays the wild's own table for j ≥ 2) and as the first real symbol with every wild before and after it; it pays the better **base** payout, then Jackpot Dance applies if that reading covers every reel. Scatters never substitute and end a run. *Rejected: "a wild copies the first real symbol; a line of wilds pays as Golden Seeds"*: then wild, wild, scatter pays nothing while wild, wild, seed pays 3 seeds, which reads as unfair. The exact EV sums over the number of leading wilds, the first real symbol and the run length. A new test tries **every** line of a small made-up machine (5 symbols incl. wild and scatter, 2–5 reels) and matches the formula to 1e-9.

**D76 — Scatters and free spins.** Symbols flagged `"scatter": true` count anywhere and never on a line; a machine's `freeSpins` or `jackpot` names which scatter starts it. Free spins play **by themselves** on the active machine with a short pause, cost nothing, keep the bet that won them, and pay ×2; a retrigger adds to the same batch. While they're waiting, auto-spin's timer stands still (it doesn't bank) and Self-Starter waits. *Rejected: free spins that keep playing on a machine you switched away from* (D61: the hamster runs one machine). Maths: the scatter count is binomial; expected spins per trigger with retriggers = N / (1 − q·N); the time they take is part of `getEconomy().extraSecondsPerSpin`, so auto profit/s (and offline earnings) stay exact. A test measures paid spins per second over 20,000 s against 1 / (interval + extra time).

**D77 — Jackpot pots: base units, growth per paid spin, a wheel decided at the trigger and paid after 3 s.** Pots are stored before the bet and payout bonuses (so changing the bet changes their shown value, like real linked jackpots), grow by `growth` on every paid spin (× Pouch Polish), and reset to their seed when won. 3+ Cheek Pouches on a **paid** spin start the wheel; the pot is picked by weight right then (like a spin's result, D11) and paid when the wheel stops. Steady-state EV = Σ (c × seed + growth): whatever flows in flows back out. *Rejected: a hidden "mystery" trigger* (no symbol to watch, no anticipation) *and pots shared by all machines* (they'd belong to no machine's balance). The wheel keeps turning after a switch and pays on its machine; retiring waits for it.

**D78 — The gamble: manual wins only, fair, never "earned", never saved.** It's offered after a win you pulled yourself that didn't start a feature, for 4 s (auto-spin waits meanwhile), and is 50/50 by the game's RNG (two cheeks: not a balance number, so it's not in data.json). **Gamble coins change your pile but never `coinsEarned`**: otherwise wins would count toward Heirloom Seeds and losses wouldn't, and gambling would farm seeds (balance rule 4 checks it). The win is paid before the offer (the event flow stays the same), so a pick needs the stake in your pile. An open gamble is left out of the save: leaving = keeping. *Rejected: gambling auto-spin wins* (a pop-up every second) *and holding the win back until you decide* (every spin would need a "collect" step).

**D79 — Hot Streak is exact too.** The next winning paid spin pays × (1 + perStack × level × min(streak, maxStacks)). The streak before a spin doesn't change that spin's odds, and in the long run P(streak ≥ k) = hᵏ, so the average bonus is perStack × (h + … + h^cap). Free spins neither count nor get the bonus. The streak is counted on every machine even without the upgrade (for the "On Fire" sticker and the stats).

**D80 — The balance pass (from the simulator): a cube-root seed curve, a smaller heirloom bonus, bets capped at ×10, pricier machines.** The first M6 draft (square root, +10% per seed, bets up to ×100, Bonanza 400K, Palace 15M) had lives collapse to **~2 minutes** by generation 7: bets, the new machines and the heirloom bonus multiply each other, so a bigger coin target only costs seconds more. Tried in the simulator (PORTING_NOTES playtest notes): the exponent alone (0.4, 1/3) barely helped; capping bets at ×10 plus a cube root made lives lengthen again after generation 10; a +3% heirloom bonus shrank the mid-game dip; higher machine prices placed the machines. Final: **seeds = floor((lifetime ÷ 1,667)^(1/3))** (1,667 keeps 3 seeds at ~45,000 coins, so the first retirement doesn't move), **+3% per seed**, **bets ×1/2/3/5/10**, **High Roller 2,000 × 10ⁿ**, **Bonanza 600,000**, **Palace 100,000,000** (and its upgrades ×10), **Bouncy Ball +3 spins at 75,000 × 2.2ⁿ** (it was never bought at +2). Idle lives now run 15–21, 11–14, 9–12 … minutes, dip to 4–8 min when the Palace arrives, then grow again. The whole tree still fills in ~1.1–1.4 h (M5 already had ~1.0–1.3 h); M7 adds tree traits, so that target is revisited there. *(Now M8, see D88.)*

**D81 — `tools/sim.mjs`: the balance simulator is now a real tool** (the old roadmap's "Balance simulator" milestone). **D82 — A click during a spin is never lost; a gamble offer takes its place.** Found in browser testing: with Wheel Training maxed the machine is idle only a split second between auto-spins, so clicks (and Space) were silently ignored and the gamble almost never appeared. If the spin you pulled just won, the gamble offer takes the queued spin's place, so you see it and your next tap decides. The queue is an input buffer (a variable in `createGame`, not in `state`, never saved). *Rejected: a "stop auto-spin" toggle* (more UI, and idle players would forget it on).

**D84 — Particles on one fixed canvas over the page (`js/fx.js`).** Whole-pixel squares in the theme's colours (read from the CSS tokens), a pool capped at 400, nothing at all with Motion "Less". **D85 — Sprites for M6, and the palette ran out of letters.** New 24×24 symbols (Hamster Wild: the hamster's face on a gold coin; Hamster Ball; Cheek Pouch; Sweet Corn; Red Apple), two machine icons and five 16×16 icons. **D86 — Save v6: the migration only bumps the version.** Every new field has a safe default that `sanitizeState` fills in (bet index 0, no free spins, pots at their seeds, streak 0, stats 0), and sanitize also cleans junk: the bet is clamped to the bet steps (and at use, to what's unlocked), pots never go below their seed, unknown pots/wheels are dropped, free spins on a machine without them are dropped, and `gamble` is never loaded. **D87 — Sampled-EV checks now allow 4 standard errors.** A 5-reel machine's EV is swung by rare huge wins (5 wilds = 150,000 on the Bonanza), so "within 3%" on 40,000–100,000 samples would fail by pure luck (on the Bonanza with 5 lines the standard error is about 8 on an EV of 268). The check is now "within max(3%, 4 standard errors of the sample)", which is honest statistics; the new brute-force test (D75) makes the formula itself exact. Rare-event checks (pot EV) test the per-pot claim "seed + growth ÷ chance when won" instead of the total, which a single Grand would swamp.

**D89 — "New seeds (carrot, sunflower, golden)" = unlockable symbols.** In the question round the user explained it as "unlockable symbols: you don't start with them, but you can unlock more, but keep it balanced in some way". **D90 — The luck model: a blank symbol, and every other symbol's weight × (1 + Luck ÷ 100).** Luck = Hamster Luck (a hamster upgrade) + Machine Luck (one per machine), shown as a number. **D91 — The gamble becomes the pokies card gamble** (the user's pick): red/black ×2 at 50%, suit ×4 at 25%, the last 5 cards shown, Take Win. **D95 — The blank (the Wood Shaving): a symbol flag, `"blank": true`, with no payout table.** It never pays, never makes a pair (so the exact hit-rate count had to learn that a pair of blanks isn't a hit), a wild can't stand in for it, and it ends a run where it lands, exactly like a scatter on a line (machine.js `endsRun`). **D96 — Symbol unlocks: `"locked": true` on the symbol + ONE `unlockSymbol` upgrade per machine that lists the symbols in the order they open** (level n opens the first n; New Seeds: Baby Carrot, then Golden Seed). The locked symbol keeps its real weight in the table (so DESIGN tables read naturally); `getSymbols` gives it weight 0 until it's open. This replaces §21's idea of reusing `symbolWeight` (weight 0 → +w): the save migration and the UI need to know which symbols are "new seeds" (the Stacker's wild is also weight 0 but isn't one), and the levels still use the one cost formula (rule 3). **Why a fixed order:** a new symbol takes probability from every other symbol, and it hurts the most valuable long runs most. With a free order, opening the Carrot *after* the Golden Seed LOWERED the EV at every Luck level (the Golden lines got rarer). With the order fixed, a test proves every step raises the EV and lowers the hit rate in every setup. Family weight shifts (Lucky Whiskers, Carrot Patch) skip a symbol that is still locked. *Rejected:* one upgrade per symbol (free order, the trap above), unlocking by taking weight from the blank (then an unlock would RAISE the hit rate, the opposite of the user's "new symbols make wins less likely").

**D97 — Luck is an effect type (`luck`, `perLevel`) summed per scope:** global upgrades (and later family traits) = **Hamster Luck** (the Four-Leaf Clover), machine upgrades = **Machine Luck** (one horseshoe-style upgrade per machine: Lucky Horseshoe, Lucky Sprinkles, Lucky Acorn, Lucky Charm). **D98 — Paytables for the unlock ladder: flat long runs for the common symbols, steep ones for the symbols you unlock.** Adding a symbol of weight w scales every other symbol's chance by f = T/(T+w), and a run of k by f^k, so a 4-in-a-row keeps only ~60% of its chance. For an unlock to raise the EV in every setup (4 reels, max Luck), the new symbol's own value must beat that loss, so its 4- and 5-runs pay a lot and the common symbols' long runs pay little more than their pairs. That's also how real pokie paytables look. The 5-reel machines got more blanks (weight 70) for fewer wins (39–47% of spins on a fresh machine) and bigger pays to keep their value.

**D99 — Sampled-EV checks now take their allowed error from the EXACT spread of one line.** The steeper M7 paytables made a sample of 40,000 Stacker spins come out 4.4 of its own "standard errors" low: rare huge wins were missing from the sample, so its spread looked smaller than it is (2 million spins matched the formula). The test now tries every possible single line of each real machine (at most 32,768), which gives the exact one-line mean (checked against the formula to 1e-9) and spread; L lines spread at most L times as much, so the bound is 4 × L × spread ÷ √N. Honest, and still tight enough to catch a wrong formula. A second brute force checks the new fast multi-line hit rate against all 46,656 grids of a toy machine.

**D115 — Big numbers: break_eternity.js behind `money.ts`, exact where plain numbers were** (step 3.7). break_eternity.js 2.1.3 (MIT, no dependencies of its own; +56 KB to the game, 14 KB zipped). `src/logic/money.ts`: `Money` is its `Decimal`, `money(x)` makes one.

- **Reading money from a save is strict.** break_eternity reads almost any text ("abc" as 0, "12abc" as 12), so `moneyFrom` only accepts the forms a Decimal writes ("1234.56", "1.5e400", "ee15.2", "(e^6)15.2"), or a plain number (older saves). Junk, NaN and Infinity give the fallback.

**D119 — Pays Both Ways, as an upgrade** (the first M7 feedback, 2026-09-27). The user: "issue with 3 slots its based left to right meaning if you get 2 on the right it doesnt count". Left to right is on purpose (D3, like a real pokie's payline), so they were asked, with the numbers: always paying both ways would take Old Clunky's hit rate from 27.7% to 40.8% and roughly double the 5-reel machines' pay, undoing M7's slog. They picked **an upgrade per machine** over *both ways always* (a full rebalance of every paytable), *keep left to right and explain it better* (a hint when a pair lands on the right) and *both ways on Old Clunky only*.
- **The rule:** each line is also scored backwards with the same `evaluate()` (wilds, blanks, scatters all as before) and that win pays on its own (`fromRight: true` in `spinResolved`). A **full line pays once** (`isFullLine`: every cell the same line symbol or a wild). The two ends may share cells: seed + 3 wilds + carrot on 5 reels pays a 4-seed run and a 4-carrot run, as "pays both ways" pokies do. *Rejected: only count a right-hand run that doesn't touch the left one* (fiddlier to explain and to make exact, for a rare case).
- **Exact maths, no simulation:** cells are independent, so a line read backwards has the same odds as one read forwards, and "full" is the same both ways. So EV both ways = EV + (EV − what full lines pay), which `expectedValue` already adds up (`fullEv`). The hit rate: a line wins when reels 1 + 2 pair or the last two do. With 4+ reels the two ends share no reel, so P(no win) = P(no left pair) × P(no right pair), each from the existing `gridHitRate` (the right end is the left-end sum on the lines backwards). With 3 reels both ends share reel 2, so `bothWaysHitRate` tries every way reel 2 can land. Tested against every line, and every grid of small toy machines (bothways.test.js).
- **`requires`** (a new, optional upgrade field): upgrade ids that must be bought first (level 1+ on the same machine). Old Clunky's needs the Third Reel, because with 2 reels every pair is already a full line. **D126 — Ways, hold & spin and the cheese wheel: how they work**
- **Ways** (`evaluateWays`): a symbol wins when it's on reel 1 and on every reel after it up to k reels (3+ for a prize), on any row; the prize × the number of ways (the matching cells on each reel multiplied). The wild never lands on reel 1 (its weight there is 0 in `rollGrid`), so a win always starts with a real symbol and the wild has no prize of its own. The EV: for each symbol and k, the product over the first k reels of its average count there (3 rows × its chance, plus the wild's on reels 2–5) × the chance the next reel has none, which is exact because the reels are independent; the hit rate is worked out reel by reel over which symbols are still "alive" (inclusion–exclusion), cached. *Rejected: paylines on every row* (the Stacker already does lines; ways is the pokie mechanic the user's "more slot machines" asked for), *Pays Both Ways on the Maze* (a ways win already reads any row; the tests check ways machines never sell it).
- **Hold & spin is decided at the start** (like a spin's result and the jackpot wheel, D92): `startHold` rolls every respin at once, stores the whole bonus in `machine.hold` (the start acorns, each acorn's value, the cells each respin filled), and a timer plays it out; it pays when it ends. So the same seed always plays the same bonus, a save made halfway loads halfway (save v10), and the view only reads `getHold()`. Spins wait for it (`spinBlocked` `bonus`), and retiring and rebuilding wait too. It starts only on paid spins, and a hold & spin win is never offered to the card gamble. *Rejected: rolling each respin as it plays* (the view's timing would change the game's random numbers, D92).
- **Its EV** (`holdSpinStats`): the trigger is the chance of 6+ acorns among the 15 cells (each cell independent); the bonus is a small table over (acorns on the board, respins left): the average acorns at the end, the chance of filling the board, and the average respins (the bonus's time is added to the machine's seconds per spin, so coins per second stay honest). Each acorn's average value is the weighted average of the value table; the Grand pays on top when the board fills.
- **The cheese wheel is rolled at resolve**: each full line picks a wedge (`rng.pickWeighted`) and its payout (and its base payout, so the win tier counts it) is × the wedge. The prize wheel on the stage then spins to it for 2.4 s and the celebration waits for it to land (view only; the coins are already paid). EV = the lines' EV + the full lines' EV × (the average wedge − 1). *Rejected: a wheel that stops the machine like the jackpot wheel* (a full line of five comes often enough that a wait on every one would slow auto-spin down).

**D136 — M11, the Hamster Casino: how it's built** (DESIGN §27).

Rejected: a steeper exponent everywhere (it would slow the first lives, which are right); slowing the income instead (the jar, stars and machines would all need new numbers, and the late game would feel smaller); a cap on seeds per life (a wall with no gradient).
- **Seeds come from this colony's coins** (`state.colonyCoins`), so a new colony starts on the curve's steep early part. **An old save's pending seeds don't change:** the v13 → v14 step sets `colonyCoins` to what the new curve needs for the seeds the old one gave (fraction and all; pure functions `seedTotal` / `seedCoins`, outside the game, so the save step can use them). Without data (a save migrated on its own) it's the lifetime coins.
- **Picked: 100 seeds, exponent 0.2** (seven variants, 20 lives × 3 seeds each: Playtest notes 1.4.0-rc.1). A later cap (300, 1,000 seeds) only stretched the last lives, where income stops growing, and left generations 11–14 at 3–6 minutes; the lower cap reaches them, and exponent 0.2 (+50% seeds takes ×7.6 the coins) matches their ×5–10 income growth. Idle generations 11–13: 2.5–7.0 → 6.9–10.3 min; active 11–15: 1.2–4.0 → 3.5–13.9. The first 8 lives and the time to the whole tree (the migration's unlock) don't change.
- **Past generation ~16 the lives climb steeply** (the simulator hits its 2-hour cap from ~18): by then the family owns everything, so income barely grows. That's meant to make the Great Migration the next step (it opens at the whole tree, at 5.0–5.8 h idle, ~generation 11–12).
- **Open (for the playtest):** a migrated family's income is × Colony Pride, but its seed curve is the same, so later colonies go much faster and their late lives are short again (colony 2's generations 9–15: 2.5–8 min idle, 1.7–4 active). If that's too fast, the levers are data: a weaker or dearer Colony Pride, or a softcap that tightens with each colony (a small code change: `seedSoftcap.seeds` ÷ something per colony).

**D149 — The golden run plays the same on every Node** (2026-09-28, found by the 1.4.0 deploy).
- **What happened:** `Math.pow` gives last-bit differences between Node 22 and Node 24 (V8 changed it: about 10% of fractional powers like the softcap's `^0.4` and `^2.5`, and whole-number ones too: Node 24 says 10^23 = 1.0000000000000001e+23). Floors, cent rounding and small amounts hide that everywhere else, which is why all 42 older checkpoints agree on both. The `migration` session fed the game `getSeedProgress().nextAt × 20` as debug coins, about 5e14, where one last bit is 0.0625 coins: the saved `colonyCoins` and `coinsEarned` came out …339.4 on Node 22 and …339.25 on Node 24. Reproduced with a Node 24 binary (the npm package `node-linux-x64@24.21.0`, unpacked in the session's scratchpad, not a project dependency): the same two checkpoints failed with the same numbers.
- **Chosen:** round the session's debug amounts to 3 significant digits before they go in (sessions.js `seedCoinsToAdd`), and re-record: only the `migration` session changed (from its first rounded amount on); the other 42 checkpoints are byte for byte the same. All 2,520 tests pass on Node 22 and Node 24, and the built game is the same file (`index-CLDqNETD.js`).
- **Rejected:** recording on Node 24 only (this session's Node 22 would then fail it, and so would any other Node that differs); a tolerance in `comparable()` (the run promises the cent; a looser test could hide a real change); a pow of our own in money.ts that gives the same bits everywhere (the right long-term fix if a real game amount ever shows the difference, but it changes the last bit of every price and payout, so the whole recording would move: a bigger change to plan with the user).
- **The rule** (AGENTS.md → Testing): a session never feeds the game a power-derived amount without rounding it, and a new recording is checked on Node 24 as well.

**D151 — The Glow Up: painted scenes** (how it's built).
- **One shared painter, `paint.ts`:** a `Pixmap` (a picture as a `Uint32Array`, clipped, with holes), a `Mask` (shapes first: a ball shaded from the top-left, a bevelled box) coloured by a `Ramp` with an outline round each shape, dithering, and colours read from theme tokens (hex or rgba: room skins use rgba stripes). The Big Cage's tree (M15, `bigtree.ts`) was the model; it's left as it was.
- **`cage.ts`: the stage is one painting behind the DOM parts** (canvas at z-index 0 under the wall, bedding and floor bands, which lay the game out on top as before). A **perspective cage** (a back wall inset from the stage's edges, side walls slanting to the front corners, a plastic tray) instead of flat bars, because depth was what the flat stage lacked most. The room is muted so the machine stays the brightest thing. **The sky is a layer behind the canvas**, seen through holes (the window's panes), so its clouds can drift with a CSS animation while the painting stays still: **the painting is only redrawn when something changes** (a resize, a skin, the machine: `invalidate()`), never every frame. **The night room** (free spins) is a second painting (the day's, dimmed towards `--night`, the lamp's pool of light) that fades in with CSS opacity. *Rejected:* painting every frame (the whole stage, for drifting clouds), SVG (not pixel art).
- **`cabinet.ts`: a cabinet is painted to fit its machine** (its size comes from the DOM: the reels, rows and pots), measured with `offset*` sizes (the machine's own pixels: the rig's CSS zoom scales the canvas with everything else), repainted when a ResizeObserver sees the machine or its sign change size, or on a switch or a skin. `isolation: isolate` keeps the canvas (z-index -1) behind every part of the machine. The bulbs are a second, see-through canvas redrawn only when a bulb changes. Each machine's material and details are code (a shape per machine, a texture, decorations); colours are tokens, so machine skins still recolour Old Clunky.
- **`wheel.ts`: the wheel is repainted every frame at its angle**, at 1 painted pixel per 2 screen pixels, so the rungs and spokes stay square pixels at any angle (a CSS-rotated picture would smear them); it's a 95×106 canvas, cheap. Only when the rounded angle changes.
- **Tests:** every token the painters read is in `:root` (a missing one would paint magenta), and `cageLayout()` keeps the room's parts on the back wall at five stage sizes (tests/art.test.js).
